# CRM-BTC Project Coding Rules

## ID Handling Policy

- **Bind every value with the JavaScript type that matches its D1 column type.** Check the column type in `crm-api/migrations/` (or `PRAGMA table_info(<table>)`) before writing a query.
  - `INTEGER` columns (`id`, `*_id` foreign keys, `performed_by`): bind a number, e.g. `parseInt(value, 10)`.
  - `TEXT` columns that hold IDs (`team_members.telegram_id`, `audit_log.record_id`): bind a string, e.g. `String(value)`. Never `parseInt` these.
- JavaScript has no separate integer type, and D1 can bind a JS number as `REAL`. In a `TEXT` column that `REAL` is stored and compared as `'1.0'` instead of `'1'`, so lookups silently return no rows.
- The database enforces this: triggers reject non-digit values in `team_members.telegram_id` and `audit_log.record_id` with `... must contain digits only; bind it as a string`. If you hit that error, fix the bind, do not drop the trigger.

### Example

```js
// Correct: telegram_id is a TEXT column
await env.DB.prepare("SELECT * FROM team_members WHERE telegram_id = ?").bind(String(telegram_id)).first();

// Correct: audit_log.record_id is TEXT, performed_by is INTEGER
await env.DB.prepare(
  "INSERT INTO audit_log (action, table_name, record_id, performed_by, change_details) VALUES (?, ?, ?, ?, ?)"
)
  .bind("insert", "contacts", String(contactId), parseInt(data.created_by, 10), JSON.stringify(details))
  .run();

// Incorrect: binds a number to a TEXT column -> stored/compared as '11524164.0', never matches '11524164'
await env.DB.prepare("SELECT * FROM team_members WHERE telegram_id = ?").bind(parseInt(telegram_id, 10)).first();
```

### Rationale

Commit 05c0142 (2025-04-25) applied an "always parseInt every ID" rule to `team_members.telegram_id`. From then on `/validate-user` found no team member and the bot refused everyone. Matching the bind type to the column type avoids this.

## Schema changes

- The D1 schema lives in `crm-api/migrations/`, numbered and append-only. `0001_baseline.sql` is the schema as it was live on 2026-10-21.
- Change the schema by adding a new file (`npx wrangler d1 migrations create crm <name>` in `crm-api/`), never by editing an applied one. Never use `DROP TABLE` on data tables.
- Apply to production with `npx wrangler d1 migrations apply crm --remote` after the code that needs it is reviewed. Create a Time Travel bookmark first.

## TypeScript and RPC

- crm-api and telegram-crm are TypeScript (`src/`), strict. Wrangler bundles `.ts` itself; there is no build step.
- telegram-crm calls crm-api over RPC: `await env.crmApi.newContact({...})`. Every data operation is a method on `CrmApi` in `crm-api/src/index.ts`; input and result types are in `crm-api/src/types.ts`. Add a method there instead of an HTTP route.
- A method that can be refused for an expected reason returns a `Result`: `{ ok: true, ... }` or `{ ok: false, status, error }` with status 400/403/404/409. Check `res.ok` before using the value. Unexpected failures (D1 errors) are thrown; callers catch them.
- `worker-configuration.d.ts` is generated: run `npm run types` after changing `wrangler.toml`. `npm run typecheck` verifies it is current and runs `tsc`.

## Bot sessions

- Each Telegram chat has one Durable Object (`ChatSession` in `telegram-crm/src/chat.ts`, binding `CHATS`, named by chat id). It stores the chat's sessions and handles the chat's updates strictly one at a time; different chats run in parallel.
- Update handling lives in `processUpdate` (`telegram-crm/src/update.ts`) and reads and writes sessions only through the `SessionStore` it is given. Do not store sessions in KV: KV is eventually consistent and allows only 1,000 writes a day on the Free plan.
- Sessions are per user: storage key `session:<telegram user id>` (in a private chat the user id equals the chat id). In a group every member runs their own flow; text, `/cancel` and button presses only touch the sender's own session. The "not on the team yet" notice is also remembered per user, so in a group every newcomer is told once a day.
- Sessions expire after 24 hours of inactivity (a flow can be resumed within a working day); a chat's storage is wiped by its alarm 24 hours after its last update.
- With a valid webhook secret the Worker always answers 200, also for unknown users and on errors: any other status makes Telegram redeliver the update. Errors go to `console.error` (Workers Logs); the chat only gets "Something went wrong. Please try again later.", never a stack trace.
- Each chat remembers its last 50 `update_id`s; a redelivered update is skipped before any side effect.
- Commands are parsed as `/cmd[@BotName] [args]`; a command for another bot is ignored, `/start` is `/help`, and text starting with `/` never reaches a flow as input (unknown commands get "Unknown command").
- Only buttons of the last message sent with an inline keyboard count: the `sendMessage` that `processUpdate` gives a flow records its `message_id` as `session.keyboard_message_id`. A press on any other message only gets the notice "This button is no longer active." Error messages (`errorMessage`, "❌ …") keep the prompt's buttons valid. For text updates `session.last_callback_data` is always `null`.
- A question that was answered loses its buttons: a pressed message shows the answer below its text ("➡️ Skip"; a flow can set `session.pressed_answer` when the button text does not say it), a question answered by text just loses its buttons. `SendOptions.replace` redraws the pressed message instead of sending a new one (the community picker). Every flow keyboard gets a "✖️ Cancel" button.
- `menu:<command>` (the main menu of `/start` and `/help`), `log:<contact id>` and `log:o:<org id>` (a conversation with the organization itself), the record card buttons `show:c|o:<id>`, `edit:c|o:<id>` (`helpers/record.ts`), `status:<org id>[:<status id>]` (`flows/status.ts`) and `fu:<org id>[:<days>|x|date]` (`flows/followup.ts`; only `date` starts a session, to type a day), `spam:…` and the admins' `unblock:<id>` buttons (`/blocked`) belong to no session and work on old messages too. The ➕ Contact link under an email opens the private chat as `/start mc_<email id>`; telegram-crm asks mail-to-tg's `sender()` for the name and address and starts `/newcontact` with them.
- Button presses are checked for team membership like text; `answerCallbackQuery` is always called.

## Tests

- Run `npm test` in `crm-api/`, `telegram-crm/` and `mail-to-tg/`. Tests run in the Workers runtime with a local D1 built from the migrations; nothing touches production.
- `crm-api/test/` calls the RPC methods. `telegram-crm/test/` drives the bot with fake Telegram updates against the real crm-api code (`test/harness.ts`); Telegram and OpenStreetMap calls are stubbed.
- Add or update a test with every behaviour change. CI runs Prettier, the type check and all tests on each pull request.
