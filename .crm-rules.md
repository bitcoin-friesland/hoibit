# CRM-BTC Project Coding Rules

## ID Handling Policy

- **Bind every value with the JavaScript type that matches its D1 column type.** Check the column type in `schema.sql` (or `PRAGMA table_info(<table>)`) before writing a query.
  - `INTEGER` columns (`id`, `*_id` foreign keys, `performed_by`): bind a number, e.g. `parseInt(value, 10)`.
  - `TEXT` columns that hold IDs (`team_members.telegram_id`, `audit_log.record_id`): bind a string, e.g. `String(value)`. Never `parseInt` these.
- JavaScript has no separate integer type, and D1 can bind a JS number as `REAL`. In a `TEXT` column that `REAL` is stored and compared as `'1.0'` instead of `'1'`, so lookups silently return no rows.
- The database enforces this: triggers reject non-digit values in `team_members.telegram_id` and `audit_log.record_id` with `... must contain digits only; bind it as a string`. If you hit that error, fix the bind, do not drop the trigger.

### Example

```js
// Correct: telegram_id is a TEXT column
await env.DB.prepare("SELECT * FROM team_members WHERE telegram_id = ?")
  .bind(String(telegram_id)).first();

// Correct: audit_log.record_id is TEXT, performed_by is INTEGER
await env.DB.prepare(
  "INSERT INTO audit_log (action, table_name, record_id, performed_by, change_details) VALUES (?, ?, ?, ?, ?)"
).bind("insert", "contacts", String(contactId), parseInt(data.created_by, 10), JSON.stringify(details)).run();

// Incorrect: binds a number to a TEXT column -> stored/compared as '11524164.0', never matches '11524164'
await env.DB.prepare("SELECT * FROM team_members WHERE telegram_id = ?")
  .bind(parseInt(telegram_id, 10)).first();
```

### Rationale

Commit 05c0142 (2025-04-25) applied an "always parseInt every ID" rule to `team_members.telegram_id`. From then on `/validate-user` found no team member and the bot refused everyone. Matching the bind type to the column type avoids this.
